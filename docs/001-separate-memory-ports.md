# 001 — 为什么取指和访存用两个端口

**状态:** 事后补记。这个决定在 stage 0 做出时**没有被记录**,当时的提交信息里
列了三个"现在就要做、以后 retrofit 很贵的决定"(双向握手、状态机、显式零编码),
双端口不在其中,代码里也没有注释。它更像是照着 Sodor 和 Rocket 顺手做的。

这篇是回头把理由想清楚,包括一条**当时没看到的反对意见**。

---

## 教材为什么反而合并

Harris & Harris 的单周期处理器(图 7.12)用**分离**的指令/数据存储器 —— 因为
一拍之内既要取指又要访存,不分开就冲突。

到了多周期(图 7.27),他们**合并成一个** `Instr / Data Memory`,加一个 `AdrSrc`
mux 和一个 `OldPC` 寄存器。

合并不是随意的,是**多周期结构解锁的一次硬件复用**:FSM 保证取指和访存永远不在
同一拍,于是可以用时间换面积。这正是多周期组织的卖点之一。

同样的前提在 riscvhw 也成立 —— `sFetch` 和 `sMem` 是不同状态。所以技术上我们
**也可以**合并。

## 我们不合并的三条理由

**1. 终点要求两个主端口(最强)**

stage 3 接进 Chipyard 时,tile 挂总线的方式是 Rocket 那种:取指和访存各一个
TileLink master。合并的话核内部就要放一个仲裁器,而那个仲裁器**最后还是要在 tile
里拆开**。

这条在 stage 3 得到验证:`TLMasterAdapter` 实例化两份,核一行没改。

**2. 契约更简单**

合并端口意味着握手状态机要知道"当前这个响应属于取指还是访存"。分开之后每个端口
只服务一个来源,`reqSent` / `resp.ready` 都不用区分来源。

**3. scratchpad 上不花钱**

Xilinx 7 系列的 Block RAM 是**真正的双端口** —— 两套独立的地址/数据/使能,甚至可
以各自用不同时钟。`Scratchpad(nPorts = 2)` 分开一个端口都不多花。

## 当时没看到的反对意见

合并端口会**强制暴露一个我们后来才发现的 bug**。

教材的 `OldPC` 寄存器之所以存在,是因为共享地址线时 PC 必须存起来。如果我们合并
了,就必须在进 `sMem` 之前把访存地址锁存下来 —— **那正是后来修的那个问题**:
`dmem_req_bits_addr` 原本是组合驱动的,`MemPort` 要求 `bits` 在 `valid` 期间保持
稳定,而 stage 0 满足这一点纯属巧合(`inst` 只在 `sFetch` 变、寄存器堆只在 `sWb`
变),没有任何东西强制它。

也就是说:**合并端口会让那个 bug 在 stage 0 就写不出来**,因为共享地址线本身就逼
着你锁存。

分开端口给了"直接组合驱动"的自由,而那个自由恰好让我犯了错。

> 教材那个 `OldPC` 看起来是多周期的额外开销,实际上也是一道护栏。
> **资源约束有时候会替你排除掉错误的设计。**

## 分开 ≠ 并行

一个容易产生的误解:两个端口不等于取指和访存真的同时发生。

查 stage 3 生成的 Verilog:

```
TLXbar_MasterXbar_RiscvhwTile_i2_o1_a32d64s1k3z4u.sv
                                   ^^^^^  两进一出
```

两个 master 进,**一条路出**。出了 tile 就被交叉开关合并了。

| 层次 | 取指和访存是否并行 |
|---|---|
| 核的接口 | 两个独立端口 |
| **tile 交叉开关** | **合并成一条,开始仲裁** |
| 系统总线 | 一条 |
| DDR 控制器 | 一个,内部仲裁 |

PYNQ-Z1 的 512MB DDR3 挂在 Zynq 的 PS 侧,PL 通过 AXI HP 口访问。PL 侧有多个 AXI
从接口(S_AXI_HP0..3),但共享同一个控制器和同一片 DRAM。

**所以分开的真实意义不是并行,是不在核里做仲裁。** 交叉开关是 rocket-chip 现成
的、验证过的东西;核里自己写一个是重复劳动,还要处理"这个响应是谁的"。把复杂度
放在它该在的层次。

## 附:DDR 和双沿为什么不解决这个问题

**DDR(double data rate)** 是在时钟两个沿上传数据,目的是在同样的引脚数和频率下
把**带宽**翻倍。但它只有一套地址/命令总线、一个控制器、一个请求流 —— 取指和访存
仍然排队。

而且我们的瓶颈不是带宽:核一次只有一条指令在飞,每几拍才发一次请求。
**它是延迟受限 + 发射受限,不是带宽受限。** 带宽翻倍收益为零。

**在自己的逻辑里用双沿**(取指走上升沿、访存走下降沿)理论可行,实际不划算:

| 问题 | 后果 |
|---|---|
| 时序预算减半 | `sExec` 已经是很长的组合链,半个周期放不下 |
| 7 系列 FPGA 没有双沿触发器 | CLB 里的 FF 是单沿的,要双沿就得复制逻辑 + mux |
| 静态时序分析变复杂 | 两个沿之间的路径要单独约束 |
| `ODDR` / `IDDR` 是 I/O 原语 | 给外部接口(比如真 DDR3 PHY)用的,不是内部逻辑 |

历史上确实有设计这么做(老式两相非交叠时钟),但那是触发器很贵的年代。现在触发器
便宜、时序裕量贵,这个交易反过来了。

**真要提高这个核的性能,该做的是让它同时有多个访存在飞** —— 现在 `sFetch` 和
`sMem` 各自死等。那需要指令预取或非阻塞访存,属于微架构轴,而这个项目刻意把那条
轴压到最低。
